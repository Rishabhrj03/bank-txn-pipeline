## Quick Start

```bash
# 1. Clone / unzip and enter the project root
cd bank-txn-pipeline

# 2. Create and activate a virtual environment
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate

# 3. Install dependencies
pip install -r requirements.txt

# 4. Run the pipeline
python main.py

# 5. Run with debug logging
python main.py --log-level DEBUG

# 6. Run tests
pytest tests/ -v
```

**Requires Python 3.11+**

## Approach & Design Decisions

### Architecture

The pipeline follows **SOLID principles** and a **layered architecture**:

```
CLI (main.py)
    └── PipelineOrchestrator      ← coordinates everything
            ├── FileReader        ← raw CSV → Transaction objects
            ├── ValidationChain   ← Chain of Responsibility validators
            ├── Deduplicator      ← two-level dedup
            ├── StateManager      ← SQLite idempotency
            ├── TransactionWriter ← atomic CSV output
            └── ReportGenerator   ← txt + JSON reconciliation report
```

Each component has a **single responsibility** and is **open for extension** without
modifying existing code (add new validators/rules by writing a new class).

---

### Duplicate Detection

Two-level strategy:

| Level | Key | What it catches |
|-------|-----|----------------|
| 1 — Exact hash | SHA-256 of all content fields | Identical rows submitted twice in the same or different files |
| 2 — `ref_no` | The bank's own reference number | Same transaction resubmitted with slightly different metadata (e.g. a corrected balance field) |

**Genuine repeated transactions are preserved.** If a customer makes two ₹500
UPI payments to Zomato at the same time, the bank assigns different `ref_no`
values — both are kept. Only records that share a `ref_no` (or are bit-for-bit
identical) are flagged as duplicates.

Duplicates go to the **quarantine file** with status `DUPLICATE` and a
detailed reason so they can be reviewed and re-instated if needed.

---

### Validation & Quarantine

All validators run on every row (collect-all-errors, not fail-fast), so a
single quarantined record carries the complete list of problems:

| Validator | Rejection Reason |
|-----------|-----------------|
| `RequiredFieldsValidator` | `MISSING_REQUIRED_FIELD` |
| `DateValidator` | `INVALID_DATE` |
| `AmountValidator` | `BOTH_DEBIT_AND_CREDIT` / `NO_DEBIT_OR_CREDIT` |

The date validator tries **multiple formats** in order (configurable in YAML):
`DD-MM-YYYY`, `DD/MM/YYYY`, `YYYY-MM-DD`, `MM/DD/YYYY`, `DD-Mon-YYYY`.
After parsing, years outside `[2000, 2100]` are also rejected as implausible.

---

### Idempotency / Re-processing

**Running the pipeline multiple times on the same files is 100% safe.**

Mechanism:
1. Each input file is hashed (SHA-256 of content) before processing.
2. The hash is stored in `data/state/pipeline_state.db` (SQLite).
3. On re-run, files whose hash already exists in the state DB are **skipped**.
4. If a file's *content* changes (re-delivered correction), its hash changes →
   it will be re-processed.
5. On re-run with new files, the `Deduplicator` is seeded with ref_nos from
   the existing canonical output, preventing cross-run duplicates.

The final canonical CSV is always a **complete snapshot** (not append-only), so
it's always consistent with itself.

---

### Late Correction Handling

Files matching `*late_correction*` are detected by filename pattern (configurable).

Processing order is enforced by the orchestrator:
1. All regular batch files (sorted lexicographically → chronological by date)
2. Late correction files last

This ensures the `Deduplicator` has full knowledge of all regular-batch records
before the correction file is processed. Any transaction in the correction file
that already exists in the canonical set (by `ref_no`) is flagged as a
`DUPLICATE_REF_NO` and sent to quarantine.

The reconciliation report has a dedicated **LATE CORRECTION FILE IMPACT** section
showing how many new records were added vs. how many were duplicates.

## Output Files

### `canonical_transactions.csv`

Clean, validated, deduplicated transactions. Columns:

| Column | Description |
|--------|-------------|
| `account_number` | Bank account identifier |
| `txn_date` | Normalised date (YYYY-MM-DD) |
| `txn_time` | Transaction time (HH:MM:SS) |
| `description` | Transaction description / narration |
| `ref_no` | Bank reference number (unique key) |
| `debit` | Debit amount (blank if credit transaction) |
| `credit` | Credit amount (blank if debit transaction) |
| `balance` | Closing balance after transaction |
| `account_type` | SALARY / CURRENT / SAVINGS |
| `source_file` | Origin CSV filename (for traceability) |

### `quarantine.csv`

Same columns as canonical plus:

| Column | Description |
|--------|-------------|
| `txn_date_raw` | Original (unparsed) date string from source |
| `validation_status` | `INVALID` or `DUPLICATE` |
| `rejection_reasons` | Semicolon-separated list of reasons |
| `row_number` | Row in source file (for debugging) |
| `record_hash` | SHA-256 content hash |

### `reconciliation_report.txt` / `.json`

- Total records received, processed, rejected, duplicates removed
- Per-file breakdown
- Rejection reason counts
- Late correction impact summary

## Intentional Quirks in Sample Data

The three CSV files contain the following AS-IS quirks (as per NOTES.txt):

| File | Row | Quirk | Pipeline Action |
|------|-----|-------|----------------|
| `batch_2026-08-01.csv` | REF_INV001 | Date `32-08-2026` (impossible day) | → QUARANTINE: INVALID_DATE |
| `batch_2026-08-01.csv` | REF_BOTH01 | Both debit=5000 and credit=3000 | → QUARANTINE: BOTH_DEBIT_AND_CREDIT |
| `batch_2026-08-01.csv` | REF_NODA01 | Neither debit nor credit | → QUARANTINE: NO_DEBIT_OR_CREDIT |
| `batch_2026-08-01.csv` | REF397176 | Exact duplicate row (appears twice) | → 2nd occurrence: QUARANTINE: DUPLICATE_ROW |
| `batch_2026-08-01.csv` | REF_XFILE01 | Same row also in Aug 2 batch | → Aug 2 version: QUARANTINE: DUPLICATE_REF_NO |
| `batch_2026-08-02.csv` | REF200017 | Date `00-08-2026` (day=0 impossible) | → QUARANTINE: INVALID_DATE |
| `batch_2026-08-02.csv` | REF_NODA02 | Neither debit nor credit | → QUARANTINE: NO_DEBIT_OR_CREDIT |
| `batch_2026-08-02.csv` | REF_XFILE01 | Cross-file dup of Aug 1 row | → QUARANTINE: DUPLICATE_REF_NO |
| `batch_2026-08-04_late_correction.csv` | REF973627 | Already exists in Aug 1 canonical | → QUARANTINE: DUPLICATE_REF_NO |

**Expected reconciliation:**

| Metric | Value |
|--------|-------|
| Total records received | 61 |
| Valid + unique → canonical | 51 |
| Quarantined (invalid) | 5 |
| Quarantined (duplicates) | 5 |

## Configuration

All behaviour is controlled by `config/pipeline_config.yaml`:

```yaml
paths:
  input_dir:    data/input      # Where to look for CSV files
  output_dir:   data/output     # Canonical CSV + reports written here
  quarantine_dir: data/quarantine
  state_dir:    data/state      # SQLite state DB

input:
  file_pattern: "*.csv"
  late_correction_pattern: "*late_correction*"
  excluded_files: ["NOTES.txt"]

validation:
  date_formats:                 # Tried in order; first match wins
    - "%d-%m-%Y"
    - "%d/%m/%Y"
    - "%Y-%m-%d"
    - "%m/%d/%Y"
  year_min: 2000
  year_max: 2100

deduplication:
  primary_key: ref_no

output:
  canonical_file: canonical_transactions.csv
  quarantine_file: quarantine.csv
  reconciliation_report: reconciliation_report
```

To onboard a new data source with different column names, simply add aliases
to the `input.column_aliases` section — no code changes required.

## Key Assumptions

1. **`ref_no` is the authoritative transaction key.** The bank guarantees each
   transaction has a unique reference number. A duplicate `ref_no` signals a
   re-delivery or data error, not a legitimate separate transaction.

2. **Negative balances are valid.** Overdraft accounts can have negative
   running balances (e.g. current accounts). These are not rejected.

3. **Zero-value debit/credit treated as absent.** A `debit=0` or `credit=0`
   carries no meaningful information and is treated the same as blank.

4. **File names encode dates for sort order.** `batch_YYYY-MM-DD*.csv`
   format means lexicographic sort = chronological order, which the pipeline
   relies on for consistent dedup across files.

5. **Late correction files are identified by filename, not content.** This is
   the most reliable detection method when files arrive without embedded
   metadata.

6. **The pipeline is append-safe within a run, snapshot-safe across runs.**
   Within one run, records accumulate in memory. Across runs, the canonical
   file is fully rewritten so it's always internally consistent.

7. **Re-delivered files with identical content are skipped.** Hash-based
   idempotency means a file re-sent without changes is not re-processed,
   preventing unintentional duplication.
